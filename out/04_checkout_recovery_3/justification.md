## CREATE vs ALTER call

All 6 events in `spec.md` (`abandonment_detected`, `reminder_sent`, `reminder_opened`, `reminder_cta_clicked`, `resumed_at_step`, `reconverted`) are new occurrences, each with its own moment and its own grain — a drop being detected, a nudge being sent, opened, clicked, a user returning, and a reconversion — none of which coincide with the moment an existing baseline table (`destination_card_clicked`, `application_started`, `document_uploaded`, `pay_now_clicked`, `purchase_completed`, `search_typed`, `landing_page_scrolled`, `auth_completed`) already writes a row. `abandonment_detected.drop_step` names an *existing* funnel step the user dropped from (`document_uploaded`/`destination_card_clicked`/`application_started`/`pay_now_clicked`), but the abandonment-detection event itself fires later, asynchronously, as its own row — it is not emitted at the same instant as the original step's own row, so it is not a peer attribute of that table. `instrumentation_notes.md`'s stated convention ("one table per event, auto-created by the client event SDK") and `relationship.md`'s "Recovery" section (this spec "mints no new spec-local key… its 6 tables join on the existing `user_id`/`application_id` envelope columns plus `drop_step`/`channel`") both treat this as a standalone 6-table flow, not an amendment to any of the 8 baseline tables. Accordingly, every event gets its own `CREATE TABLE`, matching how spec 04 was already instrumented once (`tables/index.md`, `out/04_abondon_checkout_recovery_2`). No ALTER candidates were found.

## Column choices (all 6 tables)

Columns are exactly the fields `profile.md` shows for each event (the "Field × Event Grid"), plus the structural `id`/`timestamp` every event carries (the profiler's own `id_duplicates`/`unparseable_timestamps` counters imply both fields exist on every row even though they aren't listed as "observed value" fields).

- **`id` / `timestamp`** — `UUID` / `DateTime`, not nullable, matching the envelope and every existing table (`context/tables/index.md` envelope table, production `ddl.sql`).
- **`user_id`** — plain `String`, not nullable. 100% present, 100% unique per event in `profile.md`; `relationship.md` states `user_id` is universal and exactly 28 chars, and the string-type policy requires join keys to use the *plain* type of the column they join to, not a tempting `FixedString(28)`, "because `FixedString` null-pads short values and a `FixedString`-vs-`String` join can silently mismatch on messy production data." `relationship.md`'s "Recovery" section flags this spec's `user_id` as well-formed but **not yet** overlap-checked against the main funnel — kept as plain `String` precisely so that check remains possible later without a type mismatch.
- **`application_id`** — `Nullable(String)`, matching the shared envelope's exact type for this join-map column (per the string-type policy's rule that join keys must match the type of the column they join to — `application_id` is `Nullable(String)` everywhere else, including on `application_started`, the table it targets). `profile.md` shows 100% presence and 100% uniqueness in this sample (so it *could* be made non-nullable per the ClickHouse skill's `schema-types-avoid-nullable` rule), but the type-parity requirement takes precedence here since D2 (below) already flags this exact column as the highest-risk join in the system — deviating from its established `Nullable(String)` type for a presence-based optimization is not worth the consistency risk.
- **`device_type`** — `LowCardinality(String)`, not nullable (100% present in every event). 4 distinct values (`ios`, `android`, `web-user-b2c`, `Desktop`) of clearly variable byte length (3–12 chars) — ruled out for `FixedString` per the ClickHouse skill's `schema-types-lowcardinality` rule ("Reserve FixedString for strictly fixed-length data… For most low-cardinality text, LowCardinality(String) outperforms FixedString"). 4 distinct values is far under the profiler's `low_cardinality` threshold (<1,000 absolute and <10% of present rows).
- **`os`** — `LowCardinality(Nullable(String))`. Only column in this spec with a real internal null rate: 100% *field presence* but "5.1% null" (`profile.md`, every event). 4 distinct non-null values (`iOS`, `Android`, `Windows`, `Mac OS X`), variable length — `LowCardinality`, wrapped in `Nullable` because the null here is semantic (the envelope's own documented behavior: `os` is genuinely unknown for some rows, matching the baseline's own "5.95% NULL" note in `context/tables/index.md`).
- **`app_version`** — `LowCardinality(String)`, not nullable (100% present). 3 distinct values (`7.46.0`, `7.45.2`, `7.44.0`), all 6 bytes in this sample, but this is a semantic-version string, not a fixed-format code like an ISO country/currency code — a future two-digit major or minor component (e.g. `10.0.0` vs `7.5.0`) would break a fixed width silently. Per the string-type policy's own guidance to prefer `LowCardinality(String)` over `FixedString` unless the value family is a confirmed fixed-format code, `app_version` stays `LowCardinality(String)`. (Also per `known_issues.md` → K7, `app_version` "carries no temporal signal" — it is a random synthetic segment, not a release timeline, so no ordering semantics are lost by not using `Enum`.)
- **`client_lib`** — `LowCardinality(String)`, not nullable. 2 distinct values (`mobile-rn`, `web-js`), variable length.
- **`geoip_country_code`** — `LowCardinality(String)`, not nullable. 7 distinct 2-char values observed in this sample (`IN`, `AE`, `SG`, `US`, `GB`, `AU`, `SA`) — superficially a `FixedString(2)` candidate, but `context/tables/index.md`'s envelope table documents this exact column's **full** value domain as `AE AU GB IN OM OTHER QA SA SG US` — the `OTHER` catch-all bucket is 5 bytes, breaking fixed width. This is precisely the "uniform in this sample, ragged in the full domain" trap the string-type policy calls out — `FixedString(2)` would risk an insert-time truncation/mismatch the moment an `OTHER` row lands. `LowCardinality(String)` avoids that risk entirely.
- **`city`** — `LowCardinality(String)`, not nullable. 7 distinct values (`Mumbai`, `Dubai`, `Singapore`, `New York`, `London`, `Sydney`, `Riyadh`), clearly variable length (`New York` even contains a space) — never a `FixedString` candidate.
- **`destination`** — `FixedString(2)`, not nullable. 100% present; every sampled value in this event (`AU`, `JP`, `SG`, `EG`, `MY`, `TH`, `TR`, `GB`, `ID`, `AE`, …) is exactly 2 bytes, and — unlike `geoip_country_code` above — `relationship.md`'s "Destination" section gives the **complete** 27-value domain (`AE AU CA CH EG ES FR GB GR HK ID IT JP KR LK MA MV MY OM QA SA SG TH TR US VN ZA`) with no `OTHER`/catch-all exception anywhere in it. Because the full documented domain (not just this sample) is confirmed uniformly 2 bytes, `FixedString(2)` is safe here per the ClickHouse skill's `schema-types-lowcardinality` rule's own example (`country_code FixedString(2)`).
- **`drop_step`** — `LowCardinality(String)`, not nullable (100% present in all 6 tables per the field grid). 4 distinct values (`document_uploaded`, `destination_card_clicked`, `application_started`, `pay_now_clicked`), 15–25 bytes — clearly variable length, ruled out for `FixedString`. This is also the PM's primary segmentation dimension ("Reconversion rate by drop_step — which step is most recoverable?" per `spec.md`), which drives its position in `ORDER BY` (see below).
- **`channel`** — `LowCardinality(String)`, not nullable, present on 5 of 6 tables (absent from `abandonment_detected`, which fires before a channel is chosen — field grid confirms `channel = no` for that event only). 3 distinct values (`push`, `email`, `whatsapp`), variable length (4–8 bytes). Also the PM's other primary segmentation dimension ("Which channel recovers best?").
- **`hours_since_drop`** — `UInt8`, not nullable, `reminder_sent` only (field grid: `no` everywhere else). Integer range `[1, 48]` fits `UInt8`'s `0–255` range with headroom — per the ClickHouse skill's `schema-types-minimize-bitwidth` rule, this is the smallest type that accommodates the observed range (matching the baseline envelope's own `co_travelers UInt8` precedent for small bounded integers).

**Not used: `Enum8`/`Enum16`.** `drop_step` and `channel` are both small, closed-looking sets today (4 and 3 values), but per the ClickHouse skill's `schema-types-enum` guidance, `Enum` trades a real cost (a new upstream value breaks ingestion) for validation and ordering benefits this spec doesn't need — nothing in `spec.md` asks for enum-style ordering, and `drop_step`'s 4 values are themselves just the names of 4 existing funnel tables, a list that grows whenever the funnel itself is extended. `LowCardinality(String)` gets the same dictionary-encoding storage win without that ingestion risk, consistent with none of the 8 baseline tables' categoricals (`device_type`, `os`, `citizenship`, etc.) using `Enum` either.

**Deliberate deviation from the baseline's Nullable-everywhere style:** the 8 production tables make every non-key column `Nullable(String)` regardless of observed null rate. Per the ClickHouse skill's `schema-types-avoid-nullable` rule ("Nullable columns maintain a separate UInt8 column for tracking null values, increasing storage and degrading performance… avoid Nullable unless semantically required"), every column above with 100% field presence and 0% internal nulls in `profile.md` is left non-nullable; only `os` (5.1% true nulls) and `application_id` (nullable for join-type parity, see above) are `Nullable`. This is the documented "deliberate upgrade" the instrumentation policy calls for, not an unexamined default — spec 01's tables already set this precedent (`context/tables/index.md`: "the 5 Express Checkout tables... use `LowCardinality(String)` for every categorical" under D8's template).

## ORDER BY / PARTITION BY reasoning

All 6 tables use `ENGINE = MergeTree`, `PARTITION BY toYYYYMM(timestamp)`, and a D8-compliant sort key — never the baseline's `(id, timestamp, user_id)`, which `known_issues.md` → **D8** identifies as defeating the primary index because `id` is a random UUID that no query filters on.

Two sort-key variants, matching the two natural discriminators this spec's own PM questions cut by (`spec.md`: "Reconversion rate by **drop_step**" and "Which **channel** recovers best"), and matching the identical split already established for this spec in `context/tables/index.md`:

- `abandonment_detected`, `resumed_at_step`, `reconverted` → `(toDate(timestamp), drop_step, user_id, id)` — these 3 tables all carry `drop_step` as their natural cross-table join dimension (the step the user dropped from/returned to), and none of them carry `channel` in a way that's more analytically central than `drop_step` for the questions PM will ask of them specifically (`abandonment_detected` has no `channel` at all; `resumed_at_step`/`reconverted` are the flow's endpoints, most often cut by originating `drop_step`).
- `reminder_sent`, `reminder_opened`, `reminder_cta_clicked` → `(toDate(timestamp), channel, user_id, id)` — these 3 are literally the nudge-channel funnel (open → click), so `channel` is their primary filter dimension.

Per the ClickHouse skill's `schema-pk-cardinality-order` rule, columns are ordered low-to-high cardinality: `toDate(timestamp)` (coarse date bucket) leads, then `drop_step`/`channel` (3–4 distinct values each, per `profile.md`), then `user_id` (near-100%-unique per table), then `id` (always 100% unique) last — mirroring the rule's own guideline table (`event_type, event_date, user_id, event_id`-shaped ordering). Per the `schema-pk-prioritize-filters` rule, `drop_step`/`channel` are included near the front of the key specifically because they are the columns `spec.md`'s PM questions filter/group by — a query for "reconversion rate by drop_step" or "channel funnel" hits the primary index instead of a full scan.

`PARTITION BY toYYYYMM(timestamp)` matches all 28 existing tables and stays within the ClickHouse skill's `schema-partition-low-cardinality` bound (100–1,000 partitions) — the profiled window is under a month and even years of monthly partitioning stays in the dozens, nowhere near the "too many parts" failure mode the rule warns about.

## Materialized view decision

**Not proposed.** The ClickHouse skill's `query-mv-incremental` rule frames incremental MVs as solving "read thousands of rows instead of billions" for **real-time aggregation of a single high-volume stream** — none of which applies here: the entire spec is 5,919 rows across 6 tables, several orders of magnitude below where a pre-aggregation payoff exists. More fundamentally, every PM question in `spec.md` (recovery rate by `drop_step`, channel funnel open→click→reconvert, timing effect of `hours_since_drop`) is a **cross-table** computation — `abandonment_detected` joined to `reminder_sent`/`reminder_opened`/`reminder_cta_clicked`/`resumed_at_step`/`reconverted` on `user_id`/`application_id` — and a reconversion can arrive up to 48 hours after its originating `abandonment_detected` row (`hours_since_drop` range `[1, 48]`, per `profile.md`). An incremental MV triggers per-insert-block on its *own* source table only; it cannot correctly pre-join rows that haven't arrived yet on a sibling table, so it would silently produce incomplete recovery-rate numbers for any window still inside its 48-hour tail — the same "clean, plausible, wrong" failure mode `known_issues.md` warns about elsewhere. The ClickHouse skill's other MV rule, `query-mv-refreshable` (for complex joins), exists for exactly this join shape, but a scheduled-refresh MV is still unwarranted at this row count — a direct query at analysis time is both simpler and correct, provided it uses set-membership counting rather than `windowFunnel` (see **D1** below).

## Risks / caveats to carry forward

- **D1** — `windowFunnel`/`sequenceMatch` loses conversions on this dataset because timestamps are not reliably monotonic along a funnel (confirmed on the main funnel and on Express Checkout's `pay_now_clicked`→`purchase_completed` step). This spec's own 6-table step-through chain has **not yet** been monotonicity-checked (`context/tables/index.md`: "unverified row-count ratios… no `analysis/qNN.md` file exists yet for this spec"). Any future computation of recovery rate, channel funnel, or `hours_since_drop` effect **must** use set-membership joins (`uniqExact`/`IN`), not `windowFunnel`, until monotonicity is separately verified.
- **D2** — this spec's `application_id` is the 32-char unhyphenated-hex NDJSON format, and the mandatory overlap check already returned **0% overlap** against `application_started` on all 6 tables (`out/04_abondon_checkout_recovery_2/load_report.md`, 2026-08-02). Per D2's own action table this is a **STOP**: do not join any of these 6 tables to the main funnel via `application_id`; analyse the recovery flow standalone, as spec 04 was already treated once.
- **D6** — no repeat users/events holds for this spec's population as instrumented (one row per user per table, per `relationship.md`'s "Recovery" row counts: 2,300 users in `abandonment_detected`, 2,300 in `reminder_sent`, etc., all matching distinct-user counts) — retention/repeat-nudge questions beyond this spec's own funnel should be refused with explanation rather than answered with zeros, per D6's fix.
- **D8** — the baseline `(id, timestamp, user_id)` sort key defeats the primary index; this spec's tables deliberately do not inherit it (see ORDER BY reasoning above) — flagging so no future table added to this spec's family regresses to the baseline pattern.
- **D9** — `device_type` mixes casing conventions (`ios`/`android`/`web-user-b2c` lowercase vs. `Desktop` capitalized), confirmed again in this spec's own profile — any cross-table or cross-spec comparison on `device_type` must normalize case first, exactly as D9 requires for its other documented collisions (`destination` vs `citizenship`).

Two further observations from this spec's own data, not yet known-issues entries:

Per `relationship.md`'s "Recovery" section, this spec's `user_id` — unlike its `application_id` — is well-formed (28 chars, matching the universal format) and has **not yet** been overlap-checked against `destination_card_clicked`/`application_started`. That is the first join-integrity test this spec should get before assuming (as D2 already forces for `application_id`) that the whole flow is unreachable from the main funnel; `user_id` might still provide a working bridge even though `application_id` does not.

The `geoip_country_code` column, while showing only 2-byte values in this spec's own sample, carries a documented `OTHER` catch-all value elsewhere in the platform (`context/tables/index.md`'s envelope table). This spec's DDL avoids `FixedString` for that column specifically because of it (see column-choice detail above); any other new spec profiling `geoip_country_code` should apply the same caution rather than trusting a clean-looking sample.
