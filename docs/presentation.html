Our Approach

Three agents, one wiki they all read from —
and one of them corrects it first.

Every agent orients from context/, never re-derives schema or join-safety facts on its own. Instrumentation writes to it, Context maintains it, Analysis reads from it.

STAGE 1

Instrumentation Agent

Spec + NDJSON sample → designed schema, human-in-the-loop, applied to ClickHouse.

STAGE 2

Context Agent

Keeps the wiki honest — tables, metrics, known issues, relationships. Runs twice per spec.

STAGE 3

Analysis Agent

Answers PM questions from the verified wiki, concurrently, one run per question.

Two Ways In

A build-time pipeline, and a runtime ask.

Flow 1 — Instrument new data

  • Upload spec.md + events.ndjson
  • Instrumentation Agent (human-in-the-loop)
  • Context Agent publishes schema + caveats
  • Analysis Agent answers the spec's PM questions

Flow 2 — Ask a question

  • PM opens the app
  • Asks a question in plain language
  • Analysis Agent orients from the wiki
  • Gets a grounded response back
Stage 1

Instrumentation Agent

  1. Read the context layer — understand entities and existing conventions first
  2. Load ClickHouse schema-design skills/tooling
  3. Design + apply the schema from spec + raw NDJSON (human-in-the-loop)
  4. Verify the table was created and data inserted correctly
  5. Record the change as a durable, reviewable file
● ddl.sql
● justification.md
● profile.md
● load_report.md
Stage 2

Context Agent — the wiki

context/
├── index.md — entry point
├── business.md — north-star metric, funnel
├── tables/ — one file per table
├── metrics/ — one file per metric
├── known-issues/ — quirks, broken joins
└── relationship.md — join map

One file per concern, not one giant doc — diffs stay readable, agents update a single page instead of rewriting everything.

Runs twice per spec: Pass 1 publishes new schema/known-issues before Analysis runs, so it has facts to orient from. Pass 2 consolidates every finding after Analysis finishes — the single writer, so nothing races.

Stage 3

Analysis Agent

  1. Reads the context layer, the spec, and the PM's questions
  2. Runs once per question, all concurrently, read-only against context/
  3. Produces a report grounded in verified schema and known issues
● analysis/q01.md
● analysis/q02.md
● analysis/q02_report.html
● analysis/qNN.md …

Concurrent and read-only on purpose — nothing writes to the wiki mid-flight.
