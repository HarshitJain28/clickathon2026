## CREATE vs ALTER call

All 6 events in `spec.md` (`coupon_field_shown`, `coupon_entered`, `coupon_applied`, `coupon_rejected`, `discount_shown`, `checkout_with_coupon`) get their own `CREATE TABLE`. This was not a default — two existing baseline tables were checked as plausible ALTER targets first, because both already carry coupon-shaped columns:

- `pay_now_clicked` already has `coupon_applied Nullable(UInt8)` (per `ddl.sql` and `tables/pay_now_clicked.md`).
- `purchase_completed` already has `coupon_applied Nullable(UInt8)`, `coupon_name Nullable(String)`, `discount_amount Nullable(Float64)` (per `ddl.sql` and `tables/purchase_completed.md`).

`checkout_with_coupon` ("checkout proceeds… `discount_amount`, `final_value`") is the closest conceptual candidate for an ALTER onto one of these two, since it is the same *kind* of moment (paying at a — now discounted — price). It was rejected for three concrete reasons:

1. **`purchase_completed.md` itself already faced this exact question for a sibling spec and the answer was CREATE, not ALTER.** Its own text says forex (spec 05) "is a third add-on alongside insurance and plan tiers… should be instrumented consistently with them" — yet spec 05 shipped as 5 brand-new tables (`forex_offer_shown` … `forex_purchased`), never as columns added to `purchase_completed`. "Instrumented consistently" was resolved as an analysis-layer statement (compare attach rates), not a schema-layer instruction to ALTER. No comparable sentence exists anywhere calling for this spec to be merged into `pay_now_clicked` or `purchase_completed`.
2. **Precedent across all 5 prior specs is 0-for-25 tables on ALTER.** `tables/index.md` and `instrumentation_notes.md` ("one table per event, auto-created by the client event SDK") describe every one of the 25 spec tables so far as new tables, including several that are clearly sub-steps of the same checkout/payment journey Express Checkout's `otp_entered`/`express_payment_confirmed` parallel `pay_now_clicked`/`purchase_completed` conceptually, and still got their own tables.
3. **Grain mismatch.** `checkout_with_coupon` fires with its own `id`/`timestamp`/`cart_value`/`final_value` for every checkout in this spec's 2026-06-08→2026-06-28 sample (987 rows) — a materially different population and window from the live `pay_now_clicked` table (14,739 rows, 2026-01-01→2026-07-01). There's no signal in `spec.md` that this row is emitted *at* the same client-side tap as `pay_now_clicked`/`purchase_completed`, only that it's the checkout step that happens after the coupon is applied — its own moment in this spec's own mini-funnel, not a second write to an existing row.

Conclusion: every event is a new occurrence with its own grain (confirmed by `user_id` being 100% unique per event in every one of the 6 tables, per `profile.md`) → `CREATE TABLE` for all 6, none altered.

## Column choices

**Shared envelope subset** (per the "observed fields only" policy): `profile.md`'s field grid shows only `app_version`, `application_id`, `city`, `client_lib`, `destination`, `device_type`, `geoip_country_code`, `os`, `user_id` present across these events, out of the full 30-column baseline envelope. None of `app_session_id`, `device`, `geoip_subdivision_1_code`, `client_ip`, `latitude`/`longitude`, `locale`/`language`, `funnel_type`, `co_travelers`, `is_guest`/`is_referral`/`is_enterprise`, `gclid`/`fbclid`/`gad_source`, `citizenship`, `is_back_filled`, `duplicate_id` appear anywhere in `profile.md` for this spec — they are omitted, not defaulted-in "for consistency." `id`/`timestamp` are included on every table as the universal structural columns every existing table has (profiler's own `id_duplicates`/`time_span` stats presuppose them).

- **`user_id` → `String`, not nullable.** Matches `relationship.md`'s "non-null on every row… exactly 28 characters everywhere" and the join-key-type rule: must match the existing `user_id` column's type exactly, even though `user_id` is 100% unique per event here (2,100/2,100, 987/987, etc.) confirming one-row-per-user-per-event, same shape as every existing table (D6-consistent).
- **`application_id` → `Nullable(String)`, not `FixedString`.** 100% present in every event per `profile.md`, and its sampled values are the 32-char unhyphenated hex form (`00b15b85794f4dd101aa8907ab20d349` in `checkout_with_coupon`'s sample) — the exact D2 trap shape. Kept `Nullable(String)` anyway (not `FixedString(32)`) per the join-key-type rule: it must match `application_started.application_id`'s type (`Nullable(String)`) even though the join is expected to fail — `FixedString` would only be safe for a spec-local key that never needs to compare against the DB's 36-char hyphenated form.
- **`device_type`, `app_version`, `client_lib`, `geoip_country_code`, `city` → `LowCardinality(String)`, not nullable.** All show 100% presence (0% null) and low distinct counts well under the profiler's low_cardinality gate (4–7 distinct values on samples of 268–2,100 rows, all <<1% and <<10%): `device_type` 4, `app_version` 3, `client_lib` 2, `geoip_country_code` 7, `city` 7. Per `schema-types-avoid-nullable`, 0% observed null rules out `Nullable`; per `schema-types-lowcardinality`, all sit far under the 10,000-unique-value / <10%-of-rows threshold, and city names (`Mumbai`, `Singapore`, `New York`, …) are variable-length so `FixedString` is ruled out for `city` specifically.
  - **`geoip_country_code` deliberately stays `LowCardinality(String)`, not `FixedString(2)`**, even though every value observed in this spec's sample (`IN SG AE US GB AU SA`) is 2 bytes. The platform envelope (`tables/index.md`) documents this exact column's full domain elsewhere as `AE AU GB IN OM OTHER QA SA SG US` — the `OTHER` bucket is 5 bytes and would break a fixed width. This is exactly the "catch-all bucket not visible in this sample" case the column policy warns about, so `FixedString` is rejected for this column specifically.
- **`os` → `LowCardinality(Nullable(String))`.** 4 values (`iOS`, `Android`, `Mac OS X`, `Windows`) but genuinely null 6.2–7.4% across every event — matches the platform-wide `os` texture (baseline envelope: "5.95% NULL"). `Nullable` is semantically required here (unlike the 100%-present fields above) since null is a real, recurring capture gap, not absence-of-observation.
- **`destination` → `FixedString(2)`.** 14 distinct values observed (`AU AE TH FR ID US JP GB TR GR EG VN SG MY`, subset of the platform's 27), all uniform 2-byte ISO-2 codes. Unlike `geoip_country_code`, `relationship.md`'s destination entity documents the *complete* 27-value domain (`AE AU CA CH EG ES FR GB GR HK ID IT JP KR LK MA MV MY OM QA SA SG TH TR US VN ZA`) with **no `OTHER`-style exception anywhere** — so the fixed-width risk the column policy warns about does not apply to this column. This follows the exact precedent spec 05 already set and had checked: `relationship.md` records `destination` as "a deliberate upgrade from `LowCardinality(String)`" to `FixedString(2)` for the forex tables, with the same reasoning.
- **`currency` → `FixedString(3)`.** Observed values (`INR SGD AED USD GBP AUD SAR`, 7 of the platform's documented 9) are all uniform 3-byte ISO-4217 codes, and the platform's full 9-currency domain (`AED AUD GBP INR OMR QAR SAR SGD USD`, per `purchase_completed.md`) is also uniformly 3 bytes with no documented exception — same reasoning and same precedent as spec 05's `from_currency`/`to_currency` (`FixedString(3)`, per `relationship.md`).
- **`cart_value`, `discount_amount`, `final_value` → `Float64`, not nullable.** All 100% present per event; profiler reports a mixed `int`/`float` representation for `discount_amount` (e.g. `int:769, float:218` in `checkout_with_coupon`), so a float type is required to avoid truncation. `Float64` matches the platform's existing convention for every other monetary column (`value`, `amount`, `insurance_amount`, `discount_amount` on `purchase_completed`) — consistency over inventing a `Decimal` type nothing else in the schema uses.
- **`coupon_code` → `LowCardinality(String)` (not nullable) on `coupon_entered`/`coupon_applied`/`coupon_rejected`/`discount_shown`; `LowCardinality(Nullable(String))` on `checkout_with_coupon` only.** Full observed domain across the spec is 6 codes (`FREESHIP SUMMER20 FIRST10 ATLYS15 WELCOME EXPIRED5`), ragged byte length (7–8 chars, no fixed width) → `FixedString` ruled out; `LowCardinality(String)` chosen over `Enum8` because coupon codes are marketing-managed and expected to change over time (`known_issues.md` K6 already shows one of these very codes, `SUMMER20`, running as an "always-on" code rather than a fixed seasonal set) — an `Enum` would reject any new code at insert time, a real and likely-to-recur cost. Nullable only on `checkout_with_coupon`, where 62.9% of rows are null by design (`spec.md`: "`coupon_code` may be null for no-coupon baseline") — this is the `schema-types-avoid-nullable` rule's own worked example ("`discount_percent` | NULL = 'no discount'"), so `Nullable` is semantically required there specifically, not a reflexive default.
- **`discount_type` (`coupon_applied` only) → `LowCardinality(String)`, not `Enum8`.** Only 2 observed values (`percent`, `flat`), ragged length (7 vs 4 bytes, no `FixedString` case), and technically a closed set today — but `Enum8` was rejected per the skill's own guidance ("values may change frequently → `LowCardinality(String)`"): a pricing team adding a third discount shape (e.g. tiered, BOGO) is a plausible, low-friction product change, and an `Enum` mismatch on ingest is a real risk the skill flags as a cost, not merely a theoretical one.
- **`reject_reason` (`coupon_rejected` only) → `LowCardinality(String)`, same reasoning as `discount_type`.** 4 observed values (`min_cart_not_met`, `already_used`, `expired`, `invalid_code`), ragged length (7–16 bytes). Kept off `Enum8` for the same "validation reasons evolve" risk-avoidance as `discount_type`.

## ORDER BY / PARTITION BY reasoning

All 6 tables use `ENGINE = MergeTree`, `PARTITION BY toYYYYMM(timestamp)` (bounded, ≤12 partitions/year — compliant with `schema-partition-low-cardinality`), and lead `ORDER BY` with a real filter column rather than `id`, per `known_issues.md` → **D8** ("the sort key defeats the primary index… new tables must not inherit this… Lead with real filter columns"), the same fix already applied to all 25 spec-01–05 tables.

- Per `schema-pk-cardinality-order` ("order columns low-to-high cardinality") and `schema-pk-prioritize-filters` ("prioritize columns frequently used in query filters, especially those that exclude large numbers of rows"), each table's leading discriminator is chosen from the PM's own stated questions, picking the lowest-cardinality option when more than one fits:
  - `coupon_field_shown` has no `coupon_code` yet, so it leads on `device_type` (4 distinct) — the lowest-cardinality column available, ahead of `currency`/`city`/`geoip_country_code` (7 each) and `destination` (14).
  - `coupon_entered`, `coupon_applied`, `discount_shown`, `checkout_with_coupon` lead on `coupon_code` (5–6 distinct) — this is the PM's central dimension ("which codes drive volume vs erode margin… which codes work where") and is lower cardinality than `destination`/`city`/`currency`.
  - `coupon_rejected` leads on `reject_reason` (4 distinct) rather than `coupon_code` (6 distinct here, since `EXPIRED5` only appears in `coupon_entered`/`coupon_rejected`) — PM explicitly asks for "top reject reasons," and it is also the lower-cardinality choice for this specific table.
- `(toDate(timestamp), <discriminator>, user_id, id)` mirrors the exact template used by all of specs 01–05 (`tables/index.md`'s physical-layout section), keeping `timestamp` truncated to `Date` (16-bit vs 32-bit, per `schema-pk-cardinality-order`'s own tip) and `user_id`/`id` as the higher-cardinality tail columns.
- `checkout_with_coupon` is the one exception requiring `SETTINGS allow_nullable_key = 1`, because its leading column, `coupon_code`, is `Nullable`. This is deliberate, not accidental: per `schema-pk-prioritize-filters`, the column that "excludes large numbers of rows" for this table's dominant query (the PM's conversion-lift split, coupon vs. `coupon_code IS NULL` baseline) *is* `coupon_code`, null-inclusive — so it earns the lead slot despite the extra setting it requires.

## Materialized view decision

**Not built, for any of the 4 PM question groups.** Checked against both applicable rules:

- `query-mv-incremental` (HIGH impact) exists to avoid re-scanning "thousands… instead of billions" of rows on every dashboard load. The largest table here is `coupon_field_shown` at 2,100 rows; a `GROUP BY coupon_code` or `GROUP BY device_type` over any of these 6 tables is already sub-millisecond without pre-aggregation — the rule's stated payoff doesn't exist at this scale.
- `query-mv-refreshable` (HIGH impact) exists for "complex joins and batch workflows" needing denormalization. None of the PM's 4 questions (apply rate, conversion lift, margin cost, segment cuts) require a join at all — each is a single-table `GROUP BY`/`countIf` over one of these 6 tables, or (for conversion lift) a `user_id`/`application_id` set-membership comparison the Analytics Agent can run directly, per D1.
- No `metrics/*.md` page defines a reusable coupon/discount formula to pre-compute around, and — same as `checkout_with_coupon`/`coupon_applied`/`discount_shown` above — no existing spec (01–05) proposed an MV either; `index.md` confirms **zero** views or materialized views exist across all 33 tables today. Nothing about this spec's scale or query shape breaks that pattern.

## Risks / caveats to carry forward

- **D2** — `application_id` is present on 100% of rows across all 6 tables but is the spec-NDJSON 32-char unhyphenated hex form (e.g. `00b15b85794f4dd101aa8907ab20d349` in `checkout_with_coupon`), not the DB's 36-char hyphenated UUID. The mandatory normalize-then-overlap-check (D2's own fix query) has **not been run** against `application_started` for this spec — it must run before any cross-funnel join is attempted. Given all 5 prior specs independently returned 0% overlap, budget for the same STOP verdict and analyse this coupon flow standalone by default until that check actually runs.
- **D1** — Any funnel-shaped question over this spec's 6-event sequence (`coupon_field_shown → coupon_entered → coupon_applied`/`coupon_rejected → discount_shown → checkout_with_coupon`) must be computed by `uniqExact(user_id)` set membership, never `windowFunnel`/`sequenceMatch` — this platform's timestamps are not reliably funnel-ordered (D1's own finding on the main funnel), and no monotonicity check has been run yet for this spec's own event chain.
- **D7** — `cart_value`, `discount_amount`, and `final_value` are monetary and span at least 7 currencies in this sample (`INR SGD AED USD GBP AUD SAR`, a subset of the platform's 9). Never `sum()`/`avg()` any of the three without `GROUP BY currency` — the "margin cost: total `discount_amount`" question from `spec.md` is exactly the kind of query D7 warns returns a clean but meaningless cross-currency number.
- **D8** — followed for all 6 tables (see "ORDER BY / PARTITION BY reasoning" above); flagged here only so a reviewer can confirm compliance without re-deriving it.

- `discount_shown` and `coupon_applied` have byte-identical row counts (580/580) in `profile.md`, which is the same shape spec 03's `channel_selected`/`link_generated` turned out to be (a true 1:1 pairing, confirmed by `analysis/q01.md`). This is an unverified coincidence-or-pairing question for this spec, not yet checked by any live join — worth a first-look set-membership check before assuming the two tables always co-occur 1:1.
- Both `pay_now_clicked` (`coupon_applied Nullable(UInt8)`) and `purchase_completed` (`coupon_applied`, `coupon_name`, `discount_amount`) carry their own, separately-populated coupon signals from the original baseline load. Nothing at the schema level ties those columns to this spec's `coupon_code`/`discount_amount`/`final_value` — the two could describe the same real-world checkout inconsistently (same shape of unresolved question `relationship.md` already flags for spec 02's `co_travelers` vs. `group_size`/`travellers_submitted`). Reconciling which source is authoritative for any coupon-attach or discount-total metric is analysis-layer work, not resolved by this DDL.
